## 1. Проблема

**Що вирішуємо:** Гостю потрібен **додаток життя** (тренування + стеля грошей), а не чат «що на вечерю».

**На екран:** Home СільпоSE, whisper «два ритуали · один ритм», chip демо/підключено.

**VO (сенс, можна скоротити з shorts):**  
«Ранок уже в русі. Хочеться одного ритму: тренування і стеля на продукти. Додаток життя, щоб день збирався під рукою.»

**Не казати:** порівняння з банком/АТБ; «закінчилось» як факт; медичні обіцянки.

---

## 2. Користувач

**Для кого:** **Гість Сільпо** — людина, яка вже ходить у мережу / замовляє доставку і хоче зібрати **сьогоднішній день**: сесія + список під програму, без втрати контролю над кошиком.

**На екран:** chip статусу (чесність: демо vs підключено).

**Один рядок VO:** «Це для Гостя, який хоче ритм дня, а не ще одну пораду в чаті.»

---

## 3. Рішення

**Що створили:** **СільпоSE** — два ритуали в одному домі:

| Продукт | Обіцянка на UI |
|---------|----------------|
| **СільпоSport** | Сесія сьогодні · страви з полиці |
| **СільпоExpress** | Список з чеків · долив у кошик |

**На екран:** вказівник на «Пігнали», потім на «Замовити» (Express ще не відкривати).

**VO:** «Сільпо ес і. Два ритуали — Спорт і Експрес. Один дім тримає обидва ритми.»

---

## 4. Agent flow

**Що агент робить самостійно** vs **що підтверджує Гість:**

| Шар | Автономно | Лише після Гостя |
|-----|-----------|------------------|
| Composer + KB | Збирає програму / meal queries з контенту | Профіль, вибір програми, «Смаки», Старт сесії |
| Resolver + MCP | BOOTSTRAP кошика → `find_products_batch` (+ catalog fallback) → м’який список | qty ±, swap/add, прийняття рядків |
| Write у кошик | — | **Тільки Погодити / Додати ще** |
| Auth | Токен на сервері | OTP на auth.silpo.ua |

**Інваріант Gate:** Composer **не** бачить MCP-токен; checkout / write = null, доки немає явного confirm.

**На екран під час Sport→Express:** сесія + страви → handoff «з програми» → список з’являється в Express **до** write.

**VO-міст:** «Одним жестом у Експрес. Список іде далі з того, що вже обрав. Нічого само не летить у кошик.»

---

## 5. MCP «Сільпо»

**Каталог:** 39 tools (див. `prototype/content/tools-list.public.json`). У пітчі називайте **лише ті, що видно в сценарії**.

| Tool | Навіщо в демо |
|------|----------------|
| `silpo_get_my_shopping_cart` | BOOTSTRAP: знайти cart id |
| `silpo_get_shopping_cart_by_id` | Контекст кошика + перевірка після write + checkout links |
| `silpo_get_time_slots` | Валідація слоту в BOOTSTRAP |
| `silpo_find_products_batch` | Resolve рядків списку зі полиці |
| `silpo_get_categories*` / `silpo_get_products` / `silpo_get_popular_categories` | Fallback каталогу, якщо batch слабкий |
| `silpo_add_or_update_cart_products` | **Погодити** — єдиний write у живому сценарії |
| `silpo_get_my_offline_orders` / `silpo_get_my_online_orders` | Історія → pulse / чеки (якщо логін) |

Опційно (не в master-дублі): `silpo_get_replacements` / `silpo_get_similar_products` (swap), адреси/гілки (walk).

**На екран:** busy veil «Додаємо товари в кошик Сільпо…» + toast / лінк; або короткий jury-debug **без** raw token.

**VO:** «Токен на сервері. Список правите ви. У кошик Сільпо пишемо лише коли кажете Погодити.»

**Не казати:** «AI планує тренування через MCP» (програми/ккал = KB, не MCP).

## 6. Demo (один E2E)

**Північна зірка:** Home → Sport день (сесія + страви) → **Додати в Express** → qty ± → **Погодити** → handoff на silpo.ua.

### Кроки пальця (знімайте саме це)

1. `#/` — бренд + два ритуали  
2. **Пігнали** → день сьогодні → **Старт** (1–2 с) → scroll «Спортивний раціон»  
3. **Додати всі (N) в Express** / «Додати в Express»  
4. `#/shop` — змінити qty **±** (видно число; стеля під контролем)  
5. **Погодити N** → veil → toast / «Додати ще» / відкрити silpo.ua  

**Prep (2–3 хв до Rec):** профіль і програма вже обрані; день = сьогодні; Login A; hard refresh з актуальним `?v=`.

**Backup B-roll:** `prototype/visual-shots/21-jury-express-demo.mp4` (Express-only), якщо Sport з’їхав — не замінює master, лише страховий кусок.

## 7. Цінність

| Для | Що змінюється |
|-----|----------------|
| **Гостя** | Один день: сесія + страви з програми → редагований список під м’якою ₴-стелею → confirm → **свій** кошик Сільпо; оплата лишається в звичному checkout |
| **Бізнесу** | MCP-native поверхня, що доводить до **cart fill + checkout handoff** (не chat-advice); модульний Gate під нові life-surfaces |

**VO:** «Зібрали під твій день. Оформлення — уже в Сільпо, як завжди.»

---

## 8. Метрики

**Чесно для журі (немає валідованих Guest A/B у репо):**

| Сигнал | Як зрозуміємо, що працює |
|--------|---------------------------|
| **Доказ MCP** | Видимий tool-path: resolve + write на Погодити (veil / toast / кошик на silpo.ua) |
| **Доказ агента** | Список з’являється з програми **до** write; qty змінює Гість |
| **Продуктовий DoD** | Програма → bulk handoff → Погодити → dual-gate росте (Sport+Express у одному дні) |
| **Прототипні проксі** | Session funnel `handoffMetrics` (enter / plate / bulk / dismiss / confirm) у коді — внутрішні лічильники, не публікувати як ROI |

**Не вигадувати:** conversion %, AOV lift, retention — їх у репо немає.

**Один рядок VO:** «Успіх для нас — Гість дійшов до Погодити і побачив товари у своєму кошику Сільпо.»

## 9. Наступний крок

**Масштаб без App Store фантазій:**

1. Той самий **Gate / Composer / Resolver** — новий `surface` (наступний life-ритуал).  
2. Партнерський контент як **ContentSource** (не маркетплейс усередині SE).  
3. Більше живих Guest-сесій → замінити проксі-метрики реальними handoff→checkout подіями.

**VO (≤15 с):** «Далі — той самий Gate, новий surface. Партнери як контент. А метрики — від живих Погодити до кошика.»
